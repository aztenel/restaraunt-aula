# Эксплуатация AULA

Инструкция для администратора системы и дежурного: окружения, доступы, деплой и откат, миграции, бэкапы и
проверка восстановления, мониторинг, действия при инцидентах. Инфраструктура и сайзинг —
[infrastructure.md](infrastructure.md), разработка — [../CONTRIBUTING.md](../CONTRIBUTING.md).

Цели из ТЗ, на которые опирается документ:

| Требование | Значение | Чем обеспечено |
| --- | --- | --- |
| Доступность | 99,5 % в месяц (≈ 3 ч 39 мин простоя) | healthcheck, автовозврат при неудачном деплое, откат одной командой, алерты |
| Отклик API | p95 ≤ 300 мс | алерт `AulaApiLatencyP95High`, дашборд Grafana «AULA API» |
| Бэкапы | ежедневно, 30 дней, копия у другого провайдера | контейнер `backup`, `ops/backup/backup.sh` |
| RPO / RTO | ≤ 24 ч / ≤ 4 ч | алерт `AulaBackupStale`, ежеквартальная проверка `verify-restore.sh` |
| Деплой | через CI/CD по тегу, откат одной командой | `.github/workflows/deploy.yml`, `ops/deploy/rollback.sh` |
| Отказы интеграций | заказ принимается, внешнее действие в очереди | outbox + BullMQ, очередь неудач, раздел «Инциденты» |

## 1. Окружения

| | local | staging | production |
| --- | --- | --- | --- |
| Назначение | разработка | приёмка, демо, проверка восстановления | гости и сотрудники |
| Где | ноутбук разработчика | отдельный сервер (2 vCPU / 4 ГБ) | сервер в РК (4 vCPU / 8 ГБ), см. infrastructure.md |
| Запуск | `docker compose up -d` + `pnpm dev:*` | `docker-compose.prod.yml` | `docker-compose.prod.yml` |
| Данные | демо (`SEED_DEMO=true`) | демо; временные копии production только при проверке восстановления | реальные |
| Платежи | `payments.sandbox` | `sandbox` или тестовые терминалы Kaspi/Halyk | боевые |
| Уведомления | Mailpit, без реальных отправок | тестовые номера и чат | боевые |
| Деплой | — | автоматически при push тега `v*` | тот же тег после подтверждения в GitHub |
| Домены (пример) | localhost | staging.aula.kz, admin.staging.aula.kz, api.staging.aula.kz | aula.kz, admin.aula.kz, api.aula.kz |
| Индексация | — | запрещена (`WEB_ROBOTS_TAG=noindex,nofollow`) | разрешена |

Образы одного тега одинаковы на staging и production, кроме витрины и админки: их публичные параметры
(`NEXT_PUBLIC_*`, `VITE_*`) встраиваются при сборке, поэтому CI собирает `aula-web:<тег>-staging` и
`aula-web:<тег>-production` из одного коммита с параметрами из `ops/build-env/<окружение>.env`.

## 2. Доступы и секреты

ТЗ, «Передача проекта»: **все доступы к серверам и сервисам оформлены на юрлицо клиента, а не на разработчика**.
Разработчики получают персональные доступы с минимальными правами и лишаются их после окончания работ.

| Сервис | Владелец учётной записи | Что хранится / для чего |
| --- | --- | --- |
| GitHub-организация, репозиторий, GHCR | клиент (Owner); разработчики — члены команд | код, CI/CD, образы, секреты окружений |
| Хостинг (серверы, S3, управляемый PostgreSQL) | клиент | production, staging, основное хранилище бэкапов |
| Второй провайдер хранилища | клиент | внешняя копия бэкапов |
| Регистратор домена и DNS | клиент | aula.kz и поддомены |
| Sentry | клиент | ошибки api/worker/web/admin |
| Kaspi Pay, Halyk epay | клиент (договор эквайринга) | ключи мерчанта — в админке → Интеграции |
| WhatsApp Business API, SMS-шлюз, бот Telegram | клиент | ключи — в админке → Интеграции; бот алертов — env/monitoring.env |
| Google Analytics, Яндекс.Метрика | клиент | идентификаторы счётчиков — ops/build-env/production.env |
| Почта для Let's Encrypt (ACME_EMAIL) | ящик клиента | уведомления о сертификатах |
| Менеджер паролей | клиент | всё перечисленное + пароли crypt бэкапов, APP_ENCRYPTION_KEY |

Где лежат секреты:

| Секрет | Где | Кто меняет |
| --- | --- | --- |
| SSH-ключ деплоя, known_hosts | GitHub → Settings → Environments → `staging` / `production` → Secrets | владелец репозитория |
| JWT_SECRET, APP_ENCRYPTION_KEY, METRICS_TOKEN, DATABASE_URL, S3_* | `/opt/aula/env/api.env` на сервере (chmod 600) | администратор системы |
| Ключи провайдеров (Kaspi, Halyk, WhatsApp, SMS, iiko, Яндекс.Доставка, ЭСФ) | БД, зашифрованы `APP_ENCRYPTION_KEY`; ввод — админка → Интеграции | администратор системы (роль в админке) |
| rclone (хранилища бэкапов, пароли crypt) | `/opt/aula/env/rclone.conf` (chmod 600) | администратор системы |
| Токен Telegram-бота, пароль Grafana | `/opt/aula/env/monitoring.env` | администратор системы |
| Токен чтения GHCR на сервере | `~deploy/.docker/config.json` (docker login) | администратор системы |

Правила: секреты не коммитятся (`.env`, `env/` в `.gitignore`), не пересылаются в мессенджерах, у каждого
окружения свои значения. **Потеря `APP_ENCRYPTION_KEY` = потеря всех ключей интеграций в БД**, потеря пароля crypt =
невозможность расшифровать бэкапы: оба хранятся в менеджере паролей клиента.

Ротация:

- `JWT_SECRET` — заменить в `env/api.env`, `ops/deploy/compose.sh up -d --no-deps api worker`; все сотрудники
  перелогинятся.
- `APP_ENCRYPTION_KEY` — нельзя просто заменить: сохранённые ключи интеграций станут нечитаемы. Порядок: выписать
  настройки интеграций, заменить ключ, заново ввести ключи провайдеров в админке.
- `METRICS_TOKEN` — одновременно в `env/api.env` и `env/metrics_token`, перезапустить api и prometheus.
- Уход разработчика: удалить из GitHub-организации, удалить его SSH-ключи с серверов, сменить общие секреты,
  которые он видел (`env/*.env`), отозвать персональные токены.

## 3. Подготовка сервера (один раз на окружение)

1. **ОС и Docker.** Ubuntu Server 24.04 LTS, Docker Engine + плагин Compose v2 (официальный репозиторий Docker),
   `rsync`, `unattended-upgrades` (автоустановка обновлений безопасности), синхронизация времени (chrony/timesyncd).
2. **Пользователь и SSH.** Пользователь `deploy` в группе `docker`; вход только по ключам
   (`PasswordAuthentication no`, `PermitRootLogin no`); в `~deploy/.ssh/authorized_keys` — ключ деплоя из GitHub и
   персональные ключи администраторов.
3. **Сеть.** Открыты только 22 (лучше — с ограничением по IP), 80 и 443 (TCP) и 443/UDP (HTTP/3). PostgreSQL, Redis,
   Grafana, Prometheus наружу не публикуются.
4. **Каталог и настройки** (`/opt/aula`, владелец `deploy`):

   ```bash
   sudo install -d -o deploy -g deploy -m 750 /opt/aula
   cd /opt/aula && install -d -m 700 env
   # из репозитория (тег, который будет выкатываться): ops/, docker-compose.prod.yml, docker-compose.monitoring.yml,
   # примеры конфигурации. Дальше ops/ и compose-файлы обновляет деплой из CI.
   cp .env.example .env                                  # REGISTRY, DEPLOY_ENV, домены, ACME_EMAIL, COMPOSE_PROFILES
   cp apps/api/.env.example env/api.env                  # NODE_ENV=production|staging, секреты, DATABASE_URL, S3_*
   cp apps/web/.env.example env/web.env                  # API_INTERNAL_URL=http://api:3000, SITE_URL, SENTRY_DSN
   cp ops/backup/backup.env.example env/backup.env
   cp ops/backup/rclone.conf.example env/rclone.conf
   cp ops/monitoring/monitoring.env.example env/monitoring.env
   openssl rand -hex 32 > env/metrics_token              # то же значение — METRICS_TOKEN в env/api.env
   chmod 600 env/*.env env/rclone.conf && chmod 644 env/metrics_token
   ```

   Обязательно для `env/api.env` на сервере: `NODE_ENV` (`production` или `staging`), `LOG_LEVEL=info`,
   `JWT_SECRET` (`openssl rand -base64 48`), `APP_ENCRYPTION_KEY` (`openssl rand -base64 32`), `METRICS_TOKEN`,
   `DATABASE_URL` (`postgres://aula:<пароль>@postgres:5432/aula` при профиле `db`), `REDIS_URL=redis://redis:6379`,
   `QUEUE_DRIVER=bullmq`, `STORAGE_DRIVER=s3` и `S3_*`, `PUBLIC_WEB_URL`, `ADMIN_URL`, `API_PUBLIC_URL`
   (`https://api.aula.kz`), `CORS_ORIGINS` (домены витрины и админки), `SENTRY_DSN`, `SWAGGER_ENABLED`
   (на production — по решению клиента). Значения `.env` для staging: `DEPLOY_ENV=staging`,
   `WEB_ROBOTS_TAG=noindex,nofollow`.

5. **Реестр образов.** Токен GitHub только на чтение пакетов (`read:packages`) служебной учётной записи клиента:
   `echo <токен> | docker login ghcr.io -u <учётка> --password-stdin` (под пользователем `deploy`).
6. **DNS** — записи из [infrastructure.md](infrastructure.md#dns-и-tls) до первого деплоя: Caddy сразу выпускает
   сертификаты (нужен доступный порт 80).
7. **GitHub** (Settings → Environments):
   - `staging` и `production`: secrets `SSH_PRIVATE_KEY` (ключ деплоя, без пароля), `SSH_KNOWN_HOSTS`
     (`ssh-keyscan -p 22 <хост>`); variables `DEPLOY_HOST`, `DEPLOY_USER=deploy`, `DEPLOY_PORT=22`,
     `DEPLOY_PATH=/opt/aula`, `PUBLIC_URL` (`https://aula.kz`), `HEALTHCHECK_URL`
     (`https://api.aula.kz/api/v1/health/ready`);
   - `production`: Required reviewers — ответственные клиента/техлид; Deployment branches and tags — только теги `v*`;
   - защита `main` и тегов — см. [CONTRIBUTING.md](../CONTRIBUTING.md#обязательные-проверки-ci).
8. **Первый деплой** — push тега (раздел 4) или вручную на сервере: `ops/deploy/deploy.sh v1.0.0`.
9. **Стартовые данные** (один раз, production — без демо):

   ```bash
   ops/deploy/compose.sh run --rm --no-deps \
     -e SEED_OWNER_EMAIL=owner@aula.kz -e SEED_ADMIN_EMAIL=it@aula.kz \
     migrate node dist/cli/seed.js
   # staging: добавить -e SEED_DEMO=true
   ```

   Временные пароли собственника и администратора печатаются в выводе — передать лично, смена при первом входе.
   Затем в админке: реквизиты юрлица (БИН, банк), филиалы, интеграции (платежи, WhatsApp, SMS).
10. **Мониторинг** — раздел 9.

## 4. Деплой по тегу

```bash
git checkout main && git pull
git tag -a v1.4.0 -m "Релиз 1.4.0: промокоды, отчёт по каналам"
git push origin v1.4.0
```

Что происходит ([.github/workflows/deploy.yml](../.github/workflows/deploy.yml)):

1. Полный CI на коммите тега (lint с границами модулей, типы, unit и интеграционные тесты, OpenAPI, сборка).
2. Образы в GHCR: `aula-api:v1.4.0`, `aula-backup:v1.4.0`, `aula-web:v1.4.0-{staging,production}`,
   `aula-admin:v1.4.0-{staging,production}`.
3. **Staging** автоматически: CI копирует `docker-compose.prod.yml` и `ops/` на сервер и выполняет
   `ops/deploy/deploy.sh v1.4.0`, затем проверяет `HEALTHCHECK_URL` снаружи.
4. **Production** — после подтверждения ответственным в GitHub (Actions → запуск → Review deployments) тем же тегом.

`ops/deploy/deploy.sh <тег>` на сервере:

1. скачивает образы тега (нет в реестре — выходит, ничего не меняя);
2. поднимает Redis (и PostgreSQL при профиле `db`) и ждёт healthcheck;
3. **миграции** одноразовым контейнером `migrate`; ошибка — выход, работает прежняя версия;
4. переключает `api`, `worker`, `web`, `admin`, `backup` на новый тег; Caddy на время перезапуска держит запросы
   (повтор подключения до 30 с), поэтому гости видят задержку, а не ошибку;
5. ждёт `GET /api/v1/health/ready` = 200 **и** версию тега в `/api/v1/health/live`, ответы витрины и админки;
   не дождался за 180 с — **автоматически возвращает предыдущую версию** и завершается с ошибкой;
6. перечитывает Caddyfile, записывает `.deploy/current_tag`, `.deploy/previous_tag`, `.deploy/history.log`.

Время выкатки — 1–3 минуты. Полезное на сервере:

```bash
cd /opt/aula
ops/deploy/compose.sh ps                          # состояние контейнеров текущей версии
ops/deploy/compose.sh logs -f --tail=100 api worker
cat .deploy/current_tag .deploy/previous_tag; column -t -s $'\t' .deploy/history.log | tail
```

**Окна выкатки.** Пиковая нагрузка — вечер пятницы и предпраздничные дни. Production выкатывается вне пиков:
вторник–четверг 10:00–12:00 или после 23:00 (Asia/Almaty). Не выкатывать: пятница после 15:00, суббота, за день до
праздников (Наурыз, 8 Марта, Новый год и т.п.) и в дни крупных банкетов. Срочные исправления — по решению
ответственного с готовностью откатить.

Чек-лист релиза: CI зелёный; release notes; миграции совместимы с откатом (expand/contract); новые переменные
окружения добавлены на серверы до деплоя; проверка на staging (оформление заказа до оплаты sandbox, бронь,
банкетная заявка, вход в админку); после production — дашборд Grafana 15 минут, Sentry без новых ошибок.

## 5. Откат одной командой

```bash
cd /opt/aula && ops/deploy/rollback.sh            # на .deploy/previous_tag
ops/deploy/rollback.sh v1.3.2                     # на конкретный тег
```

Или GitHub: Actions → **Rollback** → Run workflow → окружение (+ тег). Для production действует то же подтверждение.

Откат переключает `api`, `worker`, `web`, `admin`, `backup` на прежний тег (образы берутся локально, реестр не нужен)
и проверяет здоровье. Повторный запуск без аргумента откатывает ещё на один успешный релиз назад.

**Миграции при откате не выполняются и не откатываются** — они только вперёд (ТЗ, правило 9). Предыдущая версия
работает на новой схеме. Это безопасно благодаря дисциплине **expand/contract** (обязательна для каждого PR с
миграцией, проверяется на ревью):

- релиз N только *расширяет* схему: новые таблицы, nullable-колонки или колонки с default, индексы, новые значения
  статусов; старый код их не замечает;
- удаление и переименование (*contract*) — не раньше релиза N+1, когда откат на версию без новой структуры уже не
  понадобится (обычно через 1–2 недели стабильной работы).

Когда откат не поможет: данные испорчены ошибкой новой версии — исправление новой миграцией/релизом или
восстановление (раздел 8). После отката исправление выпускается новым тегом (`v1.4.1`), откаченный тег не
переиспользуется.

## 6. Миграции

- Выполняются автоматически при деплое (контейнер `migrate`) до переключения версии; в журнале
  `platform.schema_migrations` — id, модуль, контрольная сумма, время. Параллельный запуск исключён advisory lock.
- Каждый файл применяется в своей транзакции: ошибка откатывает файл целиком, деплой останавливается, работает
  прежняя версия (частично применённые предыдущие файлы безопасны — они совместимы с прежней версией).
- Ручные правки схемы и данных на production запрещены. Исправление данных — миграцией, прошедшей ревью.
- Долгие миграции больших таблиц — в окно обслуживания, с `set local lock_timeout = '5s'` в начале файла.
  `create index concurrently` внутри транзакции невозможен; на объёмах AULA обычный индекс строится за секунды.
- Правила написания — [CONTRIBUTING.md](../CONTRIBUTING.md#миграции-только-вперёд-тз-правило-9).

## 7. Стартовые и демо-данные

`node dist/cli/seed.js` идемпотентен: создаёт недостающее (юрлицо, 2 филиала, собственник, администратор,
настройки модулей) и не трогает существующее. `SEED_DEMO=true` — демо-сотрудники, меню, залы: только local и
staging. Запуск на сервере — раздел 3, п. 9.

## 8. Бэкапы и восстановление

### Что, где, когда

| | |
| --- | --- |
| Расписание | ежедневно в 03:30 Asia/Almaty (`BACKUP_CRON`), контейнер `backup` (cron) |
| База | `pg_dump -Fc` (согласованный снимок, сжатие), проверка `pg_restore --list`, sha256, манифест (релиз, последняя миграция) |
| Файлы | S3-бакет приложения: `files/current` (зеркало) + `files/archive/<время>` (изменённые и удалённые за день версии) |
| Куда | основное хранилище (`BACKUP_PRIMARY_REMOTE`) **и** внешняя копия у другого провайдера (`BACKUP_OFFSITE_REMOTE`), оба в РК |
| Шифрование | rclone crypt на стороне сервера: провайдер видит только шифротекст |
| Хранение | 30 дней (`BACKUP_RETENTION_DAYS`), последние 7 дампов не удаляются никогда |
| Контроль | метрики `aula_backup_*` → алерты `AulaBackupFailed`, `AulaBackupStale` (> 26 ч), пульс `BACKUP_HEARTBEAT_URL` в Uptime Kuma |
| RPO | ≤ 24 ч (ежедневный бэкап); при необходимости меньше — чаще `BACKUP_CRON` или PITR управляемого PostgreSQL |

```bash
ops/deploy/compose.sh run --rm backup backup.sh                 # внеплановый бэкап (например, перед рискованным релизом)
ops/deploy/compose.sh logs --tail=100 backup                    # журнал ночного бэкапа
ops/deploy/compose.sh run --rm backup rclone lsf backup-primary:production/db/   # список дампов
```

### Восстановление production после аварии (RTO ≤ 4 ч)

Бюджет времени: сервер и Docker 30–60 мин (или существующий) → настройки из менеджера паролей 20 мин → восстановление
базы и файлов 10–30 мин (десятки минут на объёмах AULA) → деплой последнего тега 5 мин → проверка 15 мин.

1. Объявить инцидент (раздел 11), витрина недоступна или работает на неверных данных.
2. Сервер: раздел 3, п. 1–7 (новый или существующий). Если база жива, но данные испорчены — остановить запись:
   `ops/deploy/compose.sh stop api worker web`.
3. Восстановить базу в **новую** пустую базу (исходную не трогаем до окончания разбирательства):

   ```bash
   ops/deploy/compose.sh run --rm backup restore.sh \
     --from backup-primary:production \
     --target-db 'postgres://aula:<пароль>@postgres:5432/aula_restored' --create-db \
     --files-target app-s3-rw:aula-production       # только если потеряны файлы; remote с ключом на запись
   ```

   Нужен дамп на момент до порчи данных — `--dump aula-db-<время>.dump` (список: `rclone lsf .../db/`).
   Основное хранилище недоступно — `--from backup-offsite:production`.
4. `DATABASE_URL` в `env/api.env` → `.../aula_restored` (или переименовать базы в `psql`), затем
   `ops/deploy/deploy.sh <текущий тег>` — миграции догонят схему до версии кода.
5. Проверка: вход в админку, последние заказы и брони в очередях, тестовый заказ до экрана оплаты, `health/ready`.
6. Сообщить филиалам, какие данные после момента бэкапа нужно внести повторно (заказы/брони за период после
   дампа — из журналов провайдеров платежей и мессенджеров).

### Ежеквартальная проверка восстановления на staging

ТЗ: «Восстановление проверяется на тестовом стенде минимум раз в квартал». Срок: первая неделя января, апреля, июля,
октября. Источник чередуется: I и III квартал — основное хранилище, II и IV — внешнее.

Подготовка (один раз): в `env/rclone.conf` staging — remote к хранилищам **production** с ключами только на чтение
и теми же паролями crypt; в `env/backup.env` staging — `VERIFY_SOURCE_PRIMARY`, `VERIFY_SOURCE_OFFSITE`
(пример — `ops/backup/rclone.conf.example`). Staging защищён так же, как production: временная база содержит
персональные данные и удаляется скриптом сразу после проверки.

```bash
cd /opt/aula                                        # staging
ops/backup/verify-restore.sh                        # или: --source offsite
```

Скрипт восстанавливает последний дамп во временную базу `aula_restore_check_<время>`, прогоняет миграции текущей
версии, выполняет smoke-запросы (число строк ключевых таблиц, свежесть журнала действий), печатает длительность
и возраст бэкапа и пишет итог в `.deploy/restore-checks.log`. Код выхода ≠ 0 — проверка не пройдена.

Чек-лист (результат — в задаче/протоколе квартальной проверки):

- [ ] Алерты бэкапов за квартал разобраны, `AulaBackupStale`/`AulaBackupFailed` сейчас не активны
- [ ] В обоих хранилищах есть дампы за последние 30 дней, старше — удалены (`rclone lsf .../db/`)
- [ ] `verify-restore.sh --source <источник квартала>` — `Результат: PASS`
- [ ] Время восстановления данных (строка «Итого») + оценка подготовки сервера и деплоя ≤ 4 ч
- [ ] Возраст бэкапа ≤ 24 ч (RPO)
- [ ] Число строк ключевых таблиц правдоподобно (сравнить с production: заказы, брони, сотрудники)
- [ ] Выборочно: 2–3 фото блюд и 1 PDF из `files/current` открываются (`rclone cat ... | head -c 100`)
- [ ] Пароли crypt и ключи доступа к хранилищам есть в менеджере паролей клиента и действуют
- [ ] Строка из `.deploy/restore-checks.log` и выводы приложены к протоколу, найденные проблемы — в задачи

## 9. Мониторинг и оповещения

| Что | Инструмент | Где смотреть |
| --- | --- | --- |
| Ошибки приложения | Sentry (api, worker, web, admin; релиз = тег) | sentry.io / self-hosted клиента |
| Метрики и алерты | Prometheus + Alertmanager → Telegram-чат дежурных | `ops/monitoring/alerts.yml` |
| Дашборды | Grafana «AULA API»: p95, 5xx, запросы, outbox, очередь неудач, бэкап, диск, логи ошибок | SSH-туннель → http://localhost:3100 |
| Логи | pino JSON → Promtail → Loki (30 дней); `docker logs` (5 × 20 МБ на контейнер) | Grafana → Explore → Loki |
| Доступность снаружи | Uptime Kuma | SSH-туннель → http://localhost:3200 |

Запуск стека мониторинга (после production-стека):

```bash
cd /opt/aula && docker compose -f docker-compose.monitoring.yml --env-file .env up -d
ssh -L 3100:127.0.0.1:3100 -L 3200:127.0.0.1:3200 -L 9090:127.0.0.1:9090 deploy@<сервер>
```

Uptime Kuma (настраивается в интерфейсе; лучше разместить на другом сервере — например, staging проверяет
production и наоборот): HTTP(s) `https://aula.kz/` (ключевое слово — название ресторана), `https://admin.aula.kz/healthz`,
`https://api.aula.kz/api/v1/health/ready` — интервал 60 с, повтор 2, уведомление в тот же Telegram-чат; уведомления
об истечении TLS-сертификатов; Push-монитор «Бэкап» с интервалом 26 ч — его URL в `BACKUP_HEARTBEAT_URL`.
Статус-страница по этим мониторам — отчёт о доступности за месяц (SLO 99,5 %).

Алерты и первые действия:

| Алерт | Важность | Первое действие |
| --- | --- | --- |
| AulaApiDown / AulaApiNotReady | critical | `compose.sh ps`, `logs api`; БД/Redis живы? диск? после релиза — `rollback.sh` |
| AulaWebDown / AulaAdminDown | critical / warning | `logs web` / `logs admin`; после релиза — откат |
| AulaHigh5xxRate | critical | Sentry → новые ошибки релиза; маршрут в Grafana; после релиза — откат |
| AulaApiLatencyP95High | warning | Grafana «Медленные маршруты»; нагрузка/CPU; долгие запросы (`log_min_duration_statement`) |
| AulaOutboxLag / AulaOutboxBacklog | critical / warning | `compose.sh ps worker`, `logs worker`, `restart worker` |
| AulaFailedJobsOpen | warning | админка → очередь неудач: причина, после восстановления провайдера — «Повторить» |
| AulaBackupFailed / AulaBackupStale / AulaBackupMissing | critical | `logs backup`, доступ к хранилищам, свободное место; ручной `backup.sh` |
| HostDisk* / HostMemoryHigh / HostCpuHigh | warning–critical | `df -h`, `docker system df`, `docker stats`; очистка старых образов |

**SLO 99,5 %** = не более 3 ч 39 мин недоступности в месяц (≈ 50 мин в неделю). Плановые работы входят в бюджет,
поэтому выполняются вне пиков и с автоматическим возвратом при неудаче.

## 10. Логи

- API и worker пишут JSON (pino): `level`, `time`, `msg`, `requestId`, `userId`; секреты, пароли, токены, коды,
  данные карт вырезаются (`LOG_REDACT_PATHS`). Ответы внешних систем — в `platform.integration_logs`
  (админка → Интеграции → журнал) с маскированием платёжных данных.
- Каждый ответ API содержит `X-Request-Id` (его же видно в ошибке `{ error, requestId }`): поиск в Grafana →
  Explore → Loki: `{service="api"} | requestId="<id>"`.
- Ошибки за час: `{project="aula", level=~"error|fatal"}`.

## 11. Инциденты

Общий порядок: (1) подтвердить алерт в чате дежурных; (2) оценить влияние — принимаются ли заказы, работает ли
админка; (3) сообщить управляющим филиалов, если гости затронуты (шаблон: что не работает, что делать, когда
ждать); (4) устранить или обойти (откат, переключение провайдера, ручной режим); (5) после восстановления — повтор
задач из очереди неудач; (6) разбор за 2 рабочих дня: причина, хронология, действия, задачи.

Принцип архитектуры (ТЗ): **падение POS, мессенджера или платёжного провайдера не роняет сайт** — заказ
принимается, внешнее действие ставится в очередь с повторами (экспоненциальная задержка), после исчерпания
повторов — в очередь неудач, откуда его повторяют вручную.

### Платёжный провайдер недоступен (Kaspi / Halyk)

- Признаки: рост `payments.*` в очереди неудач, ошибки в журнале интеграций, жалобы «не открывается оплата».
- Заказы создаются в статусе «ожидает оплаты»; гость может выбрать оплату при получении (если включена в филиале).
- Если настроены оба провайдера: админка → Интеграции → Платежи → основной провайдер — переключить на резервный
  (можно по филиалу).
- Неоплаченные заказы отменяются через `awaitingPaymentTimeoutMinutes` (по умолчанию 20 мин, настройка филиала) —
  при длительном сбое временно увеличить. Оплата, пришедшая после отмены, возвращается автоматически.
- После восстановления: повторить задачи `payments.*` из очереди неудач; сверить статусы оплат за период сбоя с
  кабинетом провайдера (поздние вебхуки обрабатываются идемпотентно).

### Мессенджер или SMS недоступен (WhatsApp Business API, SMS-шлюз, Telegram)

- Заказы и брони принимаются; уведомления гостю копятся в очереди. При недоступности WhatsApp используется SMS.
- Персонал видит новые заказы и брони в ленте админки со звуком — работа точки не зависит от мессенджера.
- Если истёк токен/шаблон WhatsApp — обновить в админке → Интеграции.
- После восстановления: повторить задачи `notifications.*`. Устаревшие (например, напоминание о прошедшей брони) —
  «Закрыть» без повтора.

### POS недоступна

- Заказы принимаются и видны в очереди админки; кухня работает по экрану админки (как в режиме `manual`).
- При долгом сбое: админка → Интеграции → POS → переключить филиал на `manual`, чтобы не копить повторы.
- После восстановления: вернуть адаптер, повторить задачи `pos.*`; выборочно сверить заказы за период сбоя в POS
  (обработчики идемпотентны, но заказы, проведённые кухней вручную, повторять не нужно — «Закрыть»).

### Worker остановлен или завис (AulaOutboxLag)

`ops/deploy/compose.sh ps worker` → `logs --tail=200 worker` → `restart worker`. Накопленные события и задачи
обработаются автоматически, в порядке поступления. Если падает сразу после старта — откат на предыдущий тег.

### Повтор задач из очереди неудач (админка)

Роль «Администратор системы»: админка → **Система → Очередь неудач**. В списке — тип задачи, ошибка, число попыток,
данные. **«Повторить»** ставит задачу в очередь заново со сброшенным счётчиком попыток; **«Закрыть»** — пометить
решённой без повтора (задача неактуальна или выполнена вручную). То же через API:
`POST /api/v1/admin/system/failed-jobs/{id}/retry` и `.../resolve`. Метрика `aula_failed_jobs_open` и алерт
`AulaFailedJobsOpen` показывают, что остались открытые задачи.

### База данных, диск, сервер

- БД недоступна (`AulaApiNotReady`): `compose.sh ps postgres` / статус управляемого PostgreSQL; место на диске;
  `logs postgres`. Данные потеряны — раздел 8.
- Диск заполнен: `docker system df`; `docker image prune -a --filter until=720h` (оставляет образы свежих релизов),
  `docker builder prune`; логи контейнеров ограничены 5 × 20 МБ.
- Сервер недоступен: консоль провайдера; не поднимается — восстановление на новом сервере (раздел 8, RTO ≤ 4 ч).
