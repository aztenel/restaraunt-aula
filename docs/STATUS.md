# Состояние проекта AULA и как его продолжить

Дата остановки: 25.09.2026. Ветка: `claude/execute-technical-spec-zx2nyw`.
Проект остановлен по решению заказчика в рабочем состоянии: всё собрано, тесты зелёные, работа сохранена в git.
Этот документ — точка входа для того, кто будет доделывать.

## 2. Что не доделано

### 2.1. Работа, прерванная остановкой

1. **Второй пакет доработок backend** — код внесён и проходит все существующие тесты, но новые тесты на него не дописаны:
   проверка сертификата сотрудником на кассе с отдельным лимитом (не общий счётчик подбора по IP), история статусов
   платежа, имена сотрудников (`*ByName`) в согласиях/сегментах/возвратах, поиск сертификатов по покупателю,
   счётчики в сегментах, флаги подтверждения телефона в публичном филиале, способ оплаты в публичном статусе заказа,
   окно и шаг бронирования, мелкие доработки POS/отчётов/уведомлений. Проверить каждый пункт и покрыть тестами.
2. **Финальный аудит против ТЗ** выполнен только для области «Заказ и оплата» (9 замечаний, ещё не перепроверены —
   `docs/development/continuation/audit-partial-ordering-payments.json`). Остальные 7 областей не проверены.
   Скрипт аудита: `docs/development/continuation/spec-audit.workflow.js` (запускается как workflow Claude Code;
   8 независимых аудиторов по разделам ТЗ + проверка каждого серьёзного замечания).

Найденные, но не исправленные замечания аудита (заказ и оплата):

- витрина: филиал не выбирается автоматически по адресу до выбора меню (гость выбирает филиал сам, адрес только проверяется);
- инфраструктура: `NEXT_PUBLIC_GEOCODER_URL` не передаётся в сборку витрины (Dockerfile/ops/build-env) — поиск адреса выключен, остаётся точка на карте;
- автоотмена неоплаченного заказа не отменяет счёт у провайдера и не сверяет статус перед отменой;
- заказ «оплата при получении» с курьером Яндекса: наложенный платёж не передаётся в Яндекс (только в комментарии);
- мелкие: «бесконтактная доставка» передаётся в Яндекс неверным флагом; слоты доставки не учитывают время зоны;
  один набор ключей провайдера на все филиалы (франчайзи со своим терминалом); промокод не освобождается при отмене заказа с оплатой при получении; нет изменения состава оформленного заказа.

### 2.2. Что требует внешних доступов (не сделать без клиента)

- **Kaspi Pay** — API закрытый, адаптер настраиваемый, но поля/подпись подтвердить у банка (ТЗ: «уточняется у банка»).
- **Halyk ePay** — проверить на тестовом терминале; двухстадийные платежи (AUTH→CHARGE) не реализованы.
- **WhatsApp Business** — нужен верифицированный аккаунт и утверждённые шаблоны; сопоставить имена шаблонов в настройках.
- **iiko** (если POS окажется iiko), **Яндекс.Доставка**, **ИС ЭСФ + NCANode**, **1С** — адаптеры написаны по публичной
  документации и проверены только на заглушках; проверить на живых/тестовых аккаунтах.
- Заполнить реальные данные: БИН и реквизиты юрлица, координаты и часы филиалов, домены (`ops/build-env/*.env`),
  реестр образов, команды в `CODEOWNERS`, секреты GitHub Environments (см. `docs/operations.md`).
- CI в GitHub Actions ни разу не запускался (проверено локально по шагам) — первый прогон может потребовать мелких правок.

### 2.3. Бэклог улучшений (не блокирует запуск)

- Ответы API: nullable-поля описаны как необязательные (`?: T | null`), фронтенды местами используют приведения типов.
- Серверные тексты (адрес доставки в очереди, заголовки ленты) только на русском.
- Анонимизация гостя: проверить полноту в отчётных проекциях.
- Переводы: часть английских SEO-текстов берётся с русского при отсутствии перевода.

## 3. Как запустить и продолжить

```bash
# окружение: Node 22, pnpm 10, Docker (или локальные PostgreSQL 16 + Redis 7)
docker compose up -d postgres redis minio mailpit
pnpm install
cp apps/api/.env.example apps/api/.env          # при необходимости поправить
pnpm --filter @aula/api migrate
SEED_DEMO=true SEED_OWNER_PASSWORD='Owner-Password-2026!' pnpm --filter @aula/api seed
pnpm dev:api        # http://localhost:3000/api/v1/docs — Swagger
pnpm dev:worker     # очереди (или QUEUE_DRIVER=inline для одного процесса)
pnpm dev:web        # http://localhost:3001
pnpm dev:admin      # http://localhost:5173 (owner@aula.kz / пароль из SEED_OWNER_PASSWORD; демо-сотрудники — Demo-Password-2026!)
```

Проверки перед любыми изменениями:

```bash
cd apps/api
npx tsc -p tsconfig.json --noEmit && npx eslint "src/**/*.ts" "test/**/*.ts"
npx vitest run --project unit
TEST_DATABASE_NAME=aula_test npx vitest run --project integration     # все модули + сквозные сценарии
pnpm -s openapi && pnpm -s openapi:lint
cd ../.. && pnpm --filter @aula/admin test && pnpm --filter @aula/web test
# браузерные e2e витрины — см. apps/web/e2e/stack.md
```

Правила разработки — `docs/development/backend-guide.md` и `docs/development/frontend-guide.md`.
Решения по гипотезам ТЗ — `docs/decisions.md` (после discovery с клиентом обновить в первую очередь).

## 4. Порядок доделки (рекомендуемый)

1. Discovery с клиентом (открытые вопросы ТЗ) → обновить `docs/decisions.md`, настройки, при необходимости адаптеры.
2. Дописать тесты второго пакета (2.1.1) и закрыть замечания аудита (2.1.2), затем прогнать аудит по остальным 7 областям.
3. Первый прогон CI на GitHub, развёртывание staging, проверка интеграций на тестовых аккаунтах (2.2).
4. Загрузка реального меню/контента/переводов, обучение персонала по `docs/admin-guide.md`, запись видео по сценарию.
5. Запуск этапами, как в ТЗ: свой канал заказа → бронь и банкеты → интеграции и аналитика.
